# Персонаж MYOR для онбординга и чата

Статус: задача подготовлена к проектированию. Дата: 06.10.2026. Основание: запрос на своего интерактивного бота и исследование Coucou / Novra Grokbot. Производственная реализация пока не начата.

## Результат

Собственный персонаж MYOR в габарите 1:1, который отражает состояние диалога / задачи и коротко реагирует на действия пользователя. Один контракт событий для веба и Expo / React Native. Внешний вид задаётся конфигурацией бэкенда; экран пользовательской кастомизации в этот этап не входит.

Персонаж может менять силуэт между округлыми и более квадратными формами. Это свойство дизайна, а не требование использовать существующую геометрию Grok или Mochi. Notch-композиция, виджеты и Live Activity не входят в первый этап.

## 1. Дизайн по собранным референсам

Подготовить 2–3 варианта собственного силуэта в квадратной рабочей области: округлый blob, squircle и свободная динамичная форма. Для каждого показать neutral, attention, thinking, success и error в размерах 48 / 64 / 160 px. Выбрать один образ для первого рига.

Входные материалы: галерея `index.html`, движения 20–34, схема 36, state machine 37 и исследования 54–60. Ранее собранные Coucou-раскадровки использовать для сравнения физики и эмоциональных переходов. Переносить принцип движения; рисовать собственные тело, глаза и детали.

Выход дизайна:

- Собственные векторные формы / слои и палитра; минимальный статический PNG fallback.
- Разметка центра, базовой линии, safe area, глаз и точек деформации. Как стартовая настройка — neutral занимает около 70–80% рабочей области; оставшийся запас нужен для растяжения.
- Карта параметров: deformation, gaze, blink, tilt, expression, palette. Уточнить диапазоны после проверки крайних поз.
- Для каждого движения — ключевые позы, время входа / цикла / выхода, правило возврата и ограничения по малым размерам.

Утверждение образа — контрольная точка перед детальной полировкой рига, а не перед всей технической подготовкой.

## 2. Короткая проверка рендерера

На простом собственном временном силуэте собрать одинаковые `idle/blink`, `thinking` и `success` двумя способами: собственный Rive и процедурный Skia. Для веба проверить соответствующий React / Canvas адаптер. Подключать зависимости в изолированную лабораторию, не заменять текущий интерфейс приложения.

Rive: editable `.rev`, runtime `.riv`, один артборд 1:1, одна основная state machine, документированный View Model. Expo development build с новым официальным RN runtime; проверить совместимость Nitro и проекта.

Skia: собственные контуры, воспроизводимые параметры движения, адаптеры native / web. Из SVG-study изучить структуру каталога и морфинга, не включать исходные Grok-данные как продуктовый ассет.

Проверить на iOS и Android development builds и в браузере: читаемость 48 / 64 px, плавность, переходы, запуск без сети, сворачивание приложения и повторный вход. Зафиксировать устройства, сборки, размер ассета, время первого появления, FPS / пропуски кадров и время автора на изменение одного движения. Цель — плавный одиночный персонаж на целевом устройстве; при доступных 60 Hz ориентир 60 fps, результат должен быть измерен.

Выход: рекомендация одного основного рендерера с причинами. Sprite atlas допустим как отдельный вариант для фиксированных клипов / запасной поставки. Экспортировать собственные кадры с прозрачностью, стабильным масштабом, pivot, fps и метаданными; не использовать WebM-кадры Novra как готовый sprite atlas.

## 3. Контракт поведения

Приложение управляет смыслом события. Рендерер преобразует состояние в позу и движение. Контракт не должен зависеть от имён таймлайнов конкретного `.riv`.

```ts
type BotState =
  | 'idle' | 'listening' | 'thinking' | 'working'
  | 'needsInput' | 'uploading' | 'success' | 'error';

type BotEmote = 'greeting' | 'acknowledge' | 'curious' | 'surprised' | 'tap';

interface BotAppearance {
  schemaVersion: 1;
  variantId: string;
  paletteId: string;
  assetVersion: string;
}

interface BotModel {
  state: BotState;
  progress?: number; // 0..1; используется только при реальном прогрессе
  appearance: BotAppearance;
  reducedMotion: boolean;
}

interface BotController {
  setModel(model: BotModel): void;
  emote(name: BotEmote, eventId: string): void;
  setGaze(x: number, y: number): void; // нормализованный ограниченный диапазон
  setActive(active: boolean): void;
  dispose(): void;
}
```

Это стартовая спецификация: окончательные типы согласовать с существующим контрактом чата / бэкенда, не вводить второй источник статуса задачи.

| Событие приложения | Состояние / реакция |
|---|---|
| Онбординг открыт впервые | Greeting, затем idle |
| Шаг онбординга завершён | Acknowledge / краткий success, затем актуальное базовое состояние |
| Пользователь готовит запрос | Listening, если интерфейс действительно знает об активности ввода |
| Сообщение отправлено | Thinking |
| Ответ поступает / задача выполняется | Working |
| Нужен ответ пользователя | NeedsInput |
| Загрузка файла начата / прогресс | Uploading; progress только при достоверных данных |
| Ответ / задача завершены | Success, затем idle или needsInput по состоянию приложения |
| Ошибка | Error; повторная попытка возвращает thinking / working |
| Тап по персонажу | Короткий tap-emote, затем актуальное базовое состояние |

Правила: error / needsInput имеют приоритет над декоративными реакциями. Повтор одного `eventId` не запускает реакцию повторно. Не накапливать неограниченную очередь эмоций; устаревшие декоративные реакции можно пропускать. После one-shot возвращаться к **текущему** состоянию приложения, включая изменившееся во время анимации. На мобильном курсор заменяется намеренным gaze на область действия; постоянное отслеживание каждого движения пальца не требуется.

## 4. Первая интеграция

Сделать экран лаборатории со всеми состояниями, ручными событиями и последовательностями: отправка → работа → успех; отправка → ошибка → повтор; загрузка → завершение; тап во время работы; изменение статуса во время one-shot.

После выбора рендерера подключить персонажа к одному экрану онбординга и одному месту в чате. Для списка сообщений проверить статический / ограниченно анимированный режим; не запускать полный активный риг для каждого исторического сообщения.

Конфигурация бэкенда передаёт известные `variantId`, `paletteId`, `assetVersion`; неизвестная версия даёт fallback. Исполняемую логику и произвольные JS-фрагменты в конфигурации не передавать. Доставка удалённых ассетов — только если нужна проекту; обеспечить кеш, версионирование и статическое отображение при сбое.

## Приёмка

- Свой образ и собственные ассеты; для включённых библиотек сохранены необходимые лицензии / notices.
- Силуэт и выражение читаются в 48 / 64 px. Деформации не обрезаются контейнером в проверенных крайних позах.
- Все восемь базовых состояний доступны; значимые error / needsInput / success понятны вместе с текстом интерфейса, не только по цвету.
- Переходы перечисленных сценариев корректны; быстрые повторные события, retry и смена состояния во время эмоции не оставляют персонажа в неверном статусе.
- Offscreen, unmount и background останавливают ненужное движение / обработчики; foreground восстанавливает актуальный статус.
- Reduced motion отключает декоративные циклы / сильные деформации и сохраняет понятный статус.
- iOS, Android и web проверены; результаты производительности и ограничения записаны на конкретных устройствах.
- Для выбранного рендерера переданы редактируемый исходник, runtime-ассет / исходный код, контракт параметров и инструкция изменения движения.

## Финальные артефакты

Дизайн-лист с позами; свой `.rev` + `.riv` либо процедурные контуры / код; каталог движений; renderer adapters; экран лаборатории; интеграция в онбординг и чат; результаты проверок; статический fallback. Atlas и экспорт кадров — по решению проверки рендерера.

До детальной реализации остаётся выбрать собственный образ по галерее и проверить два рендерера на устройствах. Использование оригинального Novra `.riv` в продукте потребует отдельных прав и не входит в эту задачу.
